NETWORKTEST4 ROOT-CAUSE ANALYSIS
===============================

What the supplied NetworkTest3 log proves
-----------------------------------------
The run initialized the WinSock bridge, but it ended with:

  registered=0
  sockets=0
  network-log-events=0
  dns-queued=0
  dns-completed=0
  watchdog-preemptions=0

Therefore that particular run never reached pthread_create, socket, connect,
getaddrinfo, send, or recv. The visible pauses in that file are main guest
nativeRender/JIT work (including a roughly 3.77 second level-load frame), not a
network-worker watchdog failure.

What the earlier NetworkTest2 reproduction proves
-------------------------------------------------
The earlier log did reach the CCHttpClient path:

  request payload logged
  guest worker registered
  condition signaled
  worker slice #1 returned
  worker slice #2 returned
  worker slice #3 started
  no further log output

That is the actual network freeze reproduction.

What changed from working DynarmicTest14
----------------------------------------
DynarmicTest14 advances the foreground PC past sem_post and immediately resumes
the registered HTTP worker before returning to foreground guest execution.
NetworkTest2 and NetworkTest3 instead marked the worker runnable and deferred
execution until a later frame pump. That changed synchronization ordering.
NetworkTest3 then added a hard watchdog around the deferred worker, but the
watchdog cannot help before a worker has been registered and scheduled.

NetworkTest4 correction
-----------------------
- Restore DynarmicTest14 immediate wake ordering from sem_post.
- Apply the same immediate wake to condition signal/broadcast.
- Keep NetworkTest2/3 asynchronous DNS and nonblocking WinSock handling.
- Keep frame slices and the 4 ms hard Dynarmic HaltExecution watchdog.
- Add a forensic import ring and detailed request/thread/DNS/socket trace so
  the next log identifies the exact stage even if the correction is incomplete.
